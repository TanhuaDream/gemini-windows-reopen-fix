# Gemini Windows 客户端关闭后无法重新打开：调查结论

调查日期：2026-09-27。范围：本机 Windows x64 客户端 1.11.4、1.12.3。

## 结论与边界

可以确认根因是官方客户端的退出逻辑缺陷，由特定设置和关闭操作触发。关闭诊断数据是客户端允许的正常选项，不是用户错误设置。

不能确认全部用户都受影响，也不能确定受影响人数。公开检索没有找到完全一致的官方 Windows 客户端故障公告或足够的其他用户实测。检索未命中不代表没有其他受影响用户。

同一代码、同一 Electron 版本、同一触发条件下，其他用户也会遇到该逻辑缺陷，这是基于代码的推断，不是多台电脑的实测统计。

## 官方安装包证据

- Google 更新器缓存中的 1.12.3 CRX 包 SHA-256：`c1986326c6a262f513d321b7ea3870be82035fc98f919437dbe6241d29f18846`。与更新器记录的包标识一致。
- 包内安装文件：`GeminiSetup-1.12.3_uncompressed.exe`。Windows 数字签名验证结果为 Valid，发布者为 Google LLC。调查期间仅提取和检查，没有运行该安装文件。
- 修复前的整个 `app.asar` 在上述安装文件中逐字节匹配，大小 307374 字节，SHA-256：`c535663b73061dd664de5aaca211ed190f9f12c47da24c53f5e0cb2afe02736f`。
- 1.11.4 与 1.12.3 修复前的 `main.js` 哈希相同：`c212c4d025dcff40209f80d48d9a8f11e87748b4024980f5443bf99c0015dd2c`。

这证明调查到的缺陷原本就存在于 Google 分发的安装文件中，不是本机程序文件损坏后产生的不同代码。

## 触发条件和过程

1. 客户端诊断数据选项 `diagnosticConsent` 为 false。本机是此设置，程序代码中的默认值也是 false。
2. 用户关闭最后一个主窗口，程序开始退出。
3. 客户端在 `will-quit` 回调里阻止默认退出，清理辅助进程通信，然后在诊断数据关闭的分支中同步再次调用 `app.quit()`。
4. Electron 44.2.0 的 `Browser::Quit()` 在正在退出时直接返回。其退出状态在 `will-quit` 回调返回以后才恢复，所以同步调用发生得太早，被忽略。
5. 主窗口已经销毁，主进程仍然存在。下一次点图标，被旧进程作为第二实例处理；客户端此处仅在主窗口引用存在时唤醒窗口，无法恢复已经没有窗口的状态。

诊断数据开启时，代码会走另一个异步分支，因此不能把诊断数据关闭分支的结果直接推广成全体用户都会遇到。本次未修改诊断数据选项、未启用数据上传来做实验。

## 实际验证与修复

本机原始 1.12.3 已实际复现：窗口关闭，但主进程及其子进程继续存在；日志停留在退出清理后。

修复只更改上述分支的退出调用，在主窗口已关闭、辅助通信清理完成后退出；并同步更新程序包内校验哈希。修复后已实际验证主进程完全退出、从原有图标入口重新打开、Gemini 页面加载成功。

本次调查结束前再次执行程序包检查，确认安装中的 1.12.3 仍包含该修复。修复后 `main.js` SHA-256：`67af484760f62b23a67bed3db4a689d143638127af94accf721717366dcff309`。

这是本地修复，不是 Google 已发布的正式修复。自动更新可能覆盖本地改动；现有修复工具只接受已确认的完整代码哈希，对未知新版停止操作。
